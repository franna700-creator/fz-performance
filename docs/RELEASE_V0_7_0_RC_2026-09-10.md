# FZ Performance v0.7.0 RC7

Date prepared: 10 Sep 2026  
Status: PREPARED OFF-VERCEL — NOT YET DEPLOYED

## Release objective

Make FZ Performance dynamically trustworthy before adaptive recommendation behaviour becomes automatic. v0.7 must be able to ingest newer physiology/training evidence, improve relationships over time, update longitudinal metrics and present useful canonical workout identities without rebuilding the shell.

## Core dynamic-runtime foundation (RC2 onward)

### Athlete Memory that can reconcile later
Feedback no longer has only one opportunity to find its workout. Source sync now re-evaluates recent unlinked athlete events after execution evidence has been persisted.

- clear in-session and post-session feedback can late-bind automatically;
- pre-workout CONTEXT is not force-linked;
- crowded training windows require modality/text evidence plus an ambiguity margin;
- inferred links retain confidence/reasons and create an audit `LINKED` event.

This directly addresses the 9 Sep pattern where the workout arrived in the canonical ledger but the in-session and post-session feedback remained standalone.

### Trends that cannot regress because a source response got poorer
Tredict source evidence remains append-only. The Trends derivation now uses `MONOTONIC_BEST_AVAILABLE` evidence: begin with the newest payload, then fill genuinely missing fields from older richer payloads.

This fixes the class of issue observed on 8 Sep, where a later `activity-detail` response lacked HR-zone arrays that had previously been captured. Known zone data therefore remains available to NCL rather than disappearing merely because a newer payload is sparse.

A canonical training day follows one of two states:

1. sufficient HR-zone evidence → positive/valid derived NCL; or
2. insufficient detail → `PENDING_DETAIL` / null.

It is never zero solely because detail is missing.

### Dynamic training identity
Raw source identity stays intact for provenance. The PWA derives an additional user-facing identity from raw Tredict/Garmin evidence, linked Athlete Memory, session kind and intensity distribution.

A generic source label can therefore become a useful label such as `Assault Bike · easy aerobic` when the evidence is strong enough. Low-confidence history remains generic rather than being invented.

Each canonical session also receives a descriptive historical ABSORB / MAINTAIN / ADAPT intent with confidence and basis. This is not an athlete choice or current recommendation.

### Dynamic Trends
`/api/trends/current` starts from the stable longitudinal store but overlays current canonical training evidence before returning:

- dynamic matched AET set;
- dynamic running relationship map;
- best-available NCL by day;
- adaptive-intent counts from canonical execution.

The old hard-coded 8 Sep / 9 Sep expected totals are no longer production-health rules. Those dates remain test fixtures only where they protect a known bug class.

### Dynamic Runtime Integrity
SYSTEM now reports more than source connectivity. It can surface:

- latest training evidence;
- unresolved post-session Athlete Memory relationships;
- number of late-bound observations;
- pending NCL detail;
- monotonic evidence protection;
- descriptive historical ABSORB / MAINTAIN / ADAPT mix;
- existing Tranche 4.1 materiality state.

### UI consistency
A final presentation layer harmonises controls, cards, section headings, status treatment, focus visibility, spacing and mobile stacking across TODAY / TRENDS / TRAIN / SYSTEM without changing data semantics.

## Dynamic source baseline retained

- persisted physiology/training paint first;
- Garmin physiology source check on load + 5-minute visible cadence + stale wake-up;
- Tredict/Garmin training source check on load + 5-minute visible cadence + stale wake-up;
- manual Garmin/workout refresh retained;
- successful source persistence causes immediate canonical reread of downstream views;
- routine data movement consumes zero Vercel deployments.

## Tranche 4 preparation

RC2 adds the shared ABSORB / MAINTAIN / ADAPT vocabulary and a versioned `adaptive-choice.schema.json` contract. It deliberately does **not** activate athlete override or automatic recommendation recomputation.

Target sequence:

- **4.2** — materiality-triggered, versioned recommendation recomputation;
- **4.3** — FZ recommended lane + athlete accept/override;
- **4.4** — up to three ranked workout options under each lane using recent execution/load, physiology, Athlete Memory, event phase, preferences, trajectory and measurement gaps.

## RC4 systemic / FZ design hardening

RC4 promotes two concerns to release contracts rather than discretionary polish:

- `src/fz-design-system.css` is the authoritative final visual semantics layer across TODAY, TRENDS, TRAIN and SYSTEM. It aligns the interface with the FZ mark (`#050505` / `#f5cf19`), raises readability/touch/focus consistency and uses motion only as a truthful LIVE-state cue.
- `docs/SYSTEMIC_REPAIR_STANDARD.md` defines the permanent repair discipline: fix the invariant at the earliest safe layer, propagate the correction through dependent contracts, reconcile historical/canonical data where needed and add a regression test before calling the defect fixed.

The release gate now includes design-system and systemic-invariant smoke tests in addition to the existing dynamic-runtime, late-binding, monotonic-evidence and adaptive-contract checks.

## RC4 objective-intelligence foundation
RC4 adds a dynamic event/objective graph, shared capability transfer, a canonical data-contract registry, dependency-driven invalidation and a pure reconciliation sweep. No recommendation recomputation or athlete adaptive-choice control is activated; the Tranche 4.1/4.2 boundary remains intact. Migration `005_event_objective_graph.sql` is prepared but not applied.

## RC6 event-intelligence ingestion hardening
RC6 promotes future-event handling into a formal knowledge gate. Events can be scheduled before their format is known, but unknown structure cannot influence capability priority or adaptive context. The resolver requires athlete-confirmed structure or adequate research, derives a demand fingerprint, compares the event directionally against the current primary objective and propagates only qualified context through the dependency graph.

Transfer potential and net training value are explicitly separated: overlap can be strategically supportive without proving event equivalence or justifying participation when recovery/opportunity cost is poor. Deadly Dozen UJ is resolved to the athlete-confirmed Sunday 20 Sep 2026 date; the prior external discrepancy is retained as provenance only.

## RC7 release-preparation hardening
RC7 finishes the pre-deployment 21–26 pass. It normalizes the build marker, expands the canonical data-contract registry, cross-validates refresh triggers/consumers against the runtime dependency graph, tightens CI enumeration for event-intelligence files and adds migration rehearsal evidence before an immutable release commit is frozen.
